AI 酒店库存匹配
与多渠道分销平台从供应商文件到可审计的渠道商品，构建可信的自动化闭环。

面向旅游科技公司的多供应商库存整合场景，以可靠的后端自动化流程为主线，贯通本地文件接入、数据标准化、AI 辅助匹配、商品生成、多渠道异步分发与对账。展示重点是领域建模、批处理、事务一致性、任务编排、并发控制和失败恢复；AI 是流程中的数据理解能力。

阅读指南与执行摘要

v1.1 定位调整：后端工程主导，AI 辅助自动化

本项目采用确定性工作流：由服务端状态机决定阶段推进，由 AI 处理难以规则化的名称、房型和条款理解。采用“常规自动流转，异常人工处理后恢复”的方式，不要求每次更新逐步点击，也不把 Agent 自主规划作为项目目标。本次交付仍是设计说明书；下述能力均需通过实现与测试证明。

这不是“给酒店名称做一次相似度计算”的项目。真正需要解决的是：多个供应商用不同语言、编码、房型和价格条款描述同一资产，运营如何确认它们可以归并，如何把来源不确定、有效期有限的库存变成渠道可接受的商品，又如何证明某次发布用的是哪一版数据。

核心方案

  1. 先建立事实，再调用 AI。文件原件不可变，按批次解析、校验、标准化；保留原始值、转换规则与行级来源。
  2. 以内部主数据承接外部差异。供应商酒店/房型/计划映射到租户内标准酒店、标准房型与价格计划；渠道编码独立管理。
  3. 匹配是受约束的决策。规则检索与候选排序先行，模型提供证据和结构化建议；冲突进入审核，未知不补成确定事实。
  4. 发布的是快照。审核的是确定版本、确定日期、确定条款的商品；事务外盒与幂等任务保障重试，对账保障最终状态可解释。
  5. 演示失败比只演示成功更有说服力。主动展示房型误匹配拦截、文件重复导入、超时后结果未知、重试去重、旧版本覆盖拦截和租户越权失败。

产品价值与验证方式

预期减少重复录入、发现重复酒店、降低条款错配风险，并缩短从文件到可发布商品的准备时间。作品集阶段不承诺商业 ROI；采用同一合成数据集上的“纯人工流程基线”和“系统辅助流程”计时、纠错与审核记录比较，报告样本数、硬件、模型版本和误差范围。

最小完整闭环

导入两家虚构供应商文件 → 隔离坏行 → 标准化 → 提出酒店与房型候选 → 人工批准映射 → 生成商品及差异预览 → 审核发布 → 模拟渠道写入 → 故障重试 → 对账 → 审计回放。

定位、边界与商业假设

产品定位

平台是旅游科技公司内部的库存整合与分销自动化后端及运营控制台，同时也是展示领域建模、数据处理、异步编排、事务一致性和可靠性设计的作品；AI承担流程内的数据理解任务。它连接供应侧描述与渠道侧商品规范，提供运营决策和发布编排，不以模型替代合同、库存承诺或平台准入。

范围层级包含明确边界
MVP 必须完成本地 CSV/XLSX/JSON；本地主数据种子；多供应商映射；数据质量；审核；商品快照；模拟渠道；重试/对账/审计；两个租户隔离完整演示链路，以小规模可复现优先
MVP 可选增强本地多语言向量模型；可选外部 LLM；批量建议；版本差异；导出错误报告；日历视图不阻塞无模型/离线模式，不增加真实依赖
后续扩展供应商 API、现有 PMS/CRS 连接器、真实渠道适配、增量同步、渠道回执、可订检查、订单联动需样例、授权、协议与测试环境；独立立项
当前不做支付、结算、税务申报、完整订单履约、取消退款、动态收益管理、全球酒店内容库、真实超售赔付商品分发闭环不能被宣传为交易履约平台

需要确认的商业假设

  • 租户代表一家旅行科技企业；供应商、渠道账号与内部用户均属于该租户。默认主数据也租户隔离，避免通过“共享酒店库”意外暴露合作关系。
  • 供应商提供的是分配库存、可售状态或询价型产品之一，必须在导入合同配置中标记。MVP 默认演示分配库存快照；不声称等同实时可订。
  • 演示采用每日每房净价、单一售卖币种 USD、按入住日历管理；真实税费、占用人数定价、儿童年龄政策、汇率与舍入规则需要合同定义。
  • 同一酒店不同供应商可能售卖相同物理房源；库存不因来源不同而天然可相加。未知共享关系时采取单供应来源选择或人工标记。
  • 本地文件的库存新鲜度有限。TTL 是运营风险规则，不是供应商库存真实性保证。

作品集差异点

展示的重点是完整业务链上的后端正确性：批次版本如何激活、并发更新如何协调、任务中断如何恢复、请求重复如何去重、超时如何确认结果、远端漂移如何修复。AI 为该链路提供结构化理解与匹配建议。模块化单体足以体现架构判断；在没有规模证据前不引入微服务、复杂流处理和多集群部署。

时间、金额与政策约定

  • 日期：入住/房态日使用酒店本地日期 DATE；入住区间为 [check_in, check_out)，退房日不占夜数。事件时间使用 UTC timestamptz；酒店时区使用 IANA 名称。
  • 取消：保留供应商原文及结构化阶梯；截止时间按酒店时区解释后转换 UTC。未知时区、无法解释的“当地时间”、缺失金额基数均阻断售卖，不让 LLM 猜。
  • 金额：使用 NUMERIC(18,4) 存计算值，最终按币种精度量化；MVP 固定 USD 两位，禁止浮点计算。注明净价/售价、含税/未含税和每晚/每次入住口径。
  • 占用人数：区分成人数、儿童年龄组和房间数；MVP 仅 1 间房、2 成人、无儿童，超出范围显式拒绝。
  • 条款版本：早餐人数、税费、担保、取消阶梯任一变化即产生新 rate policy version，不能覆盖历史。

功能优先级原则

P0 是闭环正确性与数据安全，缺一不能宣称 MVP 完成；P1 提升运营效率与展示深度；P2 是真实接入或规模演进。宁可减少 UI 花样，也不省略状态未知、映射复核、来源版本和库存池语义。

端到端业务场景与异常路径

自动化运行模式与人工边界

本地文件仍由用户主动上传；确认接收后系统自动推进，不意味着自动扫描磁盘或接入供应商 API。首次模板、首次实体映射与发布策略由人建立；重复更新复用已批准且事实未变的映射。人工操作形成恢复事件，流程从等待点继续，不要求重新上传或重做已成功阶段。

S01 新供应商首次导入

  1. 管理员创建供应商、定义文件契约、数据权属和默认时区/币种；运营选择文件类型与模板版本。
  2. 系统计算原始文件 SHA-256，扫描大小、格式和压缩展开限制；重复文件显示已有批次并复用，不重复激活。
  3. 预览前 50 行、工作表选择、编码/分隔符和字段映射。运营确认导入模式、日期范围、source_sequence 与生效时间。
  4. 后台流式解析并校验；酒店/房型主键冲突为阻断错误，单条无效日价格可隔离；显示总行/有效/警告/隔离数量。
  5. 解析产物进入 staging，生成匹配候选。未匹配实体只可进入审核，不能生成可发布商品。
  6. 运营确认批次激活；原子切换该供应商该覆盖范围的当前版本。审核映射后编译商品，完成审批与模拟发布。

异常：空文件→拒绝；模板漂移→暂停并要求新模板；某房型缺酒店→引用错误；批次含被隔离行的全量范围→默认禁止激活该覆盖分区，避免把坏行误当删除；显式允许部分激活时必须缩小覆盖范围并重新确认。

S02 同一酒店由两家供应商供货

供应商 A 提供英文简称，供应商 B 提供中文名称。候选按城市、地址、坐标和已有编码定位；审核员确认同一物业。房型分别映射；B 的“双床含早不可退”不能归到 A 的“大床含早可退”。供应选择策略只比较条款兼容、日期连续、时效合格的报价。跨供应来源可能共享库存时不合计。

异常：同名异店、酒店搬迁、整修更名、坐标落点不准、同一物业内公寓与酒店分开经营→进入疑似重复队列；不得依赖名字“一键全合并”。主数据合并需给出影响预览和审批，旧 ID 保留重定向与历史引用。

S03 每日库存与价格更新

运营导入 A 的 delta 文件：1/10 库存从 4 到 2，1/11 stop_sell=true。系统校验来源序号高于当前分区版本，更新 staging；激活后产生 offer 失效/重编译事件，仅生成变化日期的模拟渠道补丁。若渠道不支持增量，则按能力契约生成完整替换快照。

异常：delta 缺失日期表示“不变”；snapshot 缺失日期只有在明确覆盖范围且校验完整时才表示删除/关闭。不能把缺行自动解释为售罄。过期报价触发 stop-sell 意图与告警；远端停卖未确认前显示“关闭待确认”。

S04 批量发布与部分失败

分销经理选择 SIM-A、SIM-B，预览各渠道能力和 payload 差异。审批绑定快照与规则版本。提交创建发布计划与外盒；按酒店/渠道聚合键顺序执行。SIM-A 成功、SIM-B 超时，整体显示部分完成。查询 SIM-B 回执发现已落地，则标记成功；若确定未执行再重试，不重发已成功任务。

异常：字段不支持→不可重试；限流→等待 Retry-After；凭证错误→暂停账号并通知；查询仍无法确定→UNKNOWN + 人工处置；不得把超时直接当失败再创建另一份商品。

S05 发现错误匹配后的止损

  1. 审核员标记错误映射并冻结其后续商品编译；系统列出受影响报价、渠道、日期、快照与当前发布任务。
  2. 创建高优先级停卖快照，终止未发送旧任务；执行中任务完成后仍需通过新 revision 停卖并对账。
  3. 修订映射需再次审批；重新编译并发布新版本。历史映射和原始快照保持不可变。
  4. 若远端尚未停卖成功，持续显著展示风险；数据库回滚不能撤销外部已发生效果。真实订单后续需要独立履约补偿流程。

S06 多日入住与库存有效性

请求 1/10 入住、1/13 退房，需要 10、11、12 三晚均有价格、有效库存及合格政策；可售间数受三晚最小可用量约束。任一天 stop_sell 或缺价则不可售；入住日 CTA、退房日 CTD、最短/最长连住在正确日期检查。MVP 编译日历，可用本地查询验证多晚一致性；不承诺真实预订锁房。

S07 操作中断、恢复与并发

浏览器关闭不终止已确认的后台批次。Worker 崩溃后租约过期才允许接管；断点记录和唯一键避免重复 staging。两个审核员同时批准同一候选，后者收到 409 并刷新版本。两个文件同时激活相同覆盖分区时，通过来源序号与行锁决定，不能“最后请求获胜”。

版本策略与原子激活

  • 三层保留：raw artifact（原件字节与 hash）→ normalized snapshot（解析规则与模板版本）→ active source version（当前可用视图）。修正只产生新批次，不改旧原件。
  • 去重作用域为 tenant + supplier + contract + raw_hash + scope + mode；同文件改模板重解析应新建 processing_run，复用原件，不误判为已完成。
  • 来源 source_sequence 只在约定分区内单调；无来源序号的文件按“需确认替换”处理，不把上传时间当业务新鲜度。
  • 激活事务：锁覆盖分区 → 检查 expected_active_version → 校验来源版本 → 处理 tombstone → 切换 active pointer → 写审计与 outbox → 提交。不同分区可独立激活。
  • 取消解析可停止未提交批次；已激活数据的“撤销”是恢复某历史版本的新激活事件，并触发新商品修订与审批。
  • 每条标准化记录保存 artifact_id、sheet、row_number、raw_record_hash、template_version、normalizer_version、source_version；敏感字段不重复写进普通日志。

解析安全与资源限制（建议默认）

单次原件上限 20 MB、总行数 100,000、最多 10 工作表、单字段 16 KB、解压后总量 200 MB；这些是保护性配置建议，需要实际性能测试后调整。拒绝宏文件、嵌入对象和远程链接；不执行单元格公式。关键字段含公式时拒绝而非依赖不可信缓存。解析在隔离 Worker 中按流/批次处理，支持取消与超时；错误报告 CSV 导出需防 = + - @ 等公式注入并保留可读错误信息。

AI 辅助匹配与人工审核

职责划分：规则控制资格，模型辅助判断

AI 的价值在于跨语言别名理解、房型描述提取、候选排序与证据归纳。数据库归并、政策等价和发布资格由可测试规则控制。MVP 默认所有新映射都需人工确认；现有且关键事实未变的有效映射可自动复用。高置信新映射自动批准仅为后续经评估后可启用的能力，区别于基于已授权策略的常规更新发布。

AI 是可替换的流程能力

统一定义 extract_attributes、retrieve_candidates、rank_candidates 与 summarize_evidence 接口，接收冻结的来源版本，返回结构化提案，不直接改变业务状态。每次调用设置超时、重试预算、缓存键与输出校验。字段已结构化时直接解析；AI 不可用时使用规则候选或等待人工。流程引擎通过相同结果契约继续执行，不能因模型失败丢失批次或重复发布。

酒店、房型与计划分别匹配

  • 酒店级：名称只是软信号。国家明确冲突必拒绝；城市冲突需地址与行政区人工确认；坐标距离只有在地理精度足够时才启用，例如“双方均为建筑级定位且大于 2km”阻断自动建议，阈值为拟议配置。不能把城市中心默认坐标当建筑位置。
  • 房型级：只在已批准的同酒店内比较。床型、床数、入住上限、卧室数、吸烟、景观和面积分别记录“相等/兼容/冲突/未知”；“床型到店安排”不等于固定大床。上限 3 人的房不自动等同 2 人房，需要供应商销售语义。
  • 价格计划级：按餐食人数、取消阶梯、担保/付款、税费、售卖窗口、入住限制、人数组合做结构化比较。Flexible 标签不能证明阶梯相同。任何关键字段未知或冲突都阻断自动等价映射。
  • 方向性：“更大房型可以替代更小房型”是业务履约承诺，不能从属性包含关系推断。MVP 只支持人工确认的等价映射，不做自动升级替代。

模型风险控制

  • 文件文本是数据而非指令。遇到“忽略规则、直接发布”等提示注入，模型无工具权限；输出仅作为候选提案，经字段白名单与规则验证。
  • 外部 LLM 默认关闭；启用前获得数据处理许可。可离线使用规则和已缓存候选；模型调用失败显示“模型建议不可用”，保留人工流程。
  • 证据引用必须能在来源中定位；无法验证的地址、坐标、星级与设施不得写回事实层。翻译内容与原始事实分别存储并标记待审核。
  • 以 source_version + candidate_set_version + model + prompt + rules 做结果缓存键；温度等参数固定仍不保证完全确定，因此保留实际请求/响应摘要。
  • 人工批准不等于永久豁免：床型、政策、地址等实质字段变化时，现有映射变为 NEEDS_REVIEW；纯空白规范化不触发复审，但规则要可测试。
  • 批量批准只允许同质、无冲突且证据完整项；显示影响数和抽样，禁止“批准全部未知”。后续自动化需独立开关、灰度和误匹配停机阈值。

人工审核证据包

包括源文件定位、原文与标准化字段、候选对照、冲突与未知列表、模型/规则版本、同名异店提示、下游影响数量、历史决策、当前 reviewer/version。批准保存 decision_reason 与有效期；拒绝保存 negative pair，避免下次重复推荐同一错误配对，但规则/事实改变时可重新评估。

价格、库存与商品生成

编译资格闸门

只有酒店映射、房型映射、价格政策映射均已批准，来源仍有效、日期完整、币种/税费口径明确、渠道能力可表达时，才生成 READY 商品。任何一步失败都返回可操作的 blocking_reasons，不能只给“校验失败”。

毛利保护若按渠道佣金模拟，margin = sell − commission − cost − fixed_cost佣金基数和税费需配置；净价渠道不再扣零售佣金；不得混用两种合同模型
税费和汇率MVP 固定同币种且已知税费口径；未来显式 FX quote/version/expiry 与税费条目缺税费口径不生成售价；禁止 LLM 推断税率或悄悄换汇
库存保护publish_qty = max(0, selected_pool_qty − safety_buffer)，按渠道分配约束4 间、缓冲1，最多分配3间；SIM-A=2、SIM-B=1，共用池不得各发3间当独占

停售与限制stop_sell 覆盖数量；CTA/CTD/LOS 单独表示；过期来源触发关闭意图quantity=0 不删除房型；缺日价格不可沿用昨日值
大幅变化价格涨跌、房型/退改变化进入风险审批；规则改动产生新版本新来源替换导致不可退：直接阻断等价商品，不能只显示价格变动

商品快照结构与变更范围

快照保存 property/room/rate mapping version、source activation version、pricing rule version、allocation policy version、channel capability version、日期区间、逐日价格库存与政策。payload 做规范化排序后计算 SHA-256，剔除非业务字段如 trace_id。审批绑定此 hash；任何业务字段变化都需生成新快照并重新经过审批闸门；符合已授权策略时可由新策略决策批准，否则转人工，不沿用旧hash的审批。

对比项按内容、房型条款、价格、库存、限制分组。MVP 每个渠道 listing + 日期窗口生成完整目标快照，模拟适配器可转为逐日更新；不做“从当前数据库临时拼出审批后的内容”。

本地查询和真实可订的界线

本地 availability 查询只反映当前激活文件与已配置分配规则，响应明确包含 as_of、expires_at、simulation=true。没有供应商确认与订单占用，就不能承诺“实时有房”。未来订单链路须增加 search→price check→hold/book→confirm 与失败补偿，另行设计。

可靠发布时序

  1. API 接收 Idempotency-Key 和审批快照；校验权限、审批 hash、expected_revision 和过期时间。
  2. 同一数据库事务内创建 publish_plan、细分 task、desired_revision 和 outbox_event；唯一键约束防止重复计划。提交后立即返回 202 与查询链接。
  3. dispatcher 通过 FOR UPDATE SKIP LOCKED 取外盒，派发可重复；Worker 接管租约并根据 task 唯一标识去重。
  4. Worker 校验任务未被 supersede，按 channel_account + listing 聚合键串行；适配器转换快照、拆分请求并携带稳定业务幂等键。
  5. 模拟器在远端事务内校验幂等键、payload hash、revision；写远端状态与 receipt 后返回。同 key 不同 payload 返回 409。
  6. 本地记录回执、applied_revision 和任务结果。Worker 在远端成功后崩溃，恢复时查询同幂等键，获得相同 receipt，不重复创建。
  7. 对账按优先级扫描 desired/applied/observed；成功回执不替代实际读取比对。部分失败汇总但不回滚其他渠道已成功操作。

业务任务唯一键：tenant + channel_account + listing + desired_revision + chunk_index
远端请求键：SHA256(tenant | channel_account | listing | revision | action | chunk_index)

if same_key and same_payload_hash: return original_operation

旧任务与迟到写入

本地串行不足以阻止超时请求迟到。模拟器必须在远端比较 revision，拒绝较旧版本，并在写入事务中原子更新。真实渠道若没有幂等、查询、CAS 或等价顺序保证，只能降低并发、等待不确定请求收敛并持续对账；仍存在残余覆盖风险，应写入接入评估，不虚构通用 exactly-once 保证。

三方对账

desired 是审批后的目标；applied 是已确认发送成功；observed 是实际读取远端的状态。比较单位是租户、渠道账号、listing、日期、人数及 policy hash，远端读取失败归为 UNKNOWN，不归为“缺失”。

  • 远端缺失 / 数值漂移：若目标仍有效且任务已完成，创建“重新应用同一已批准快照”的修复任务，引用原审批；若业务值变化则需新审批。
  • 本地已撤回而远端仍售卖：最高优先级停卖 + 告警；所有自动修复必须尊重新的 desired_revision，不能复活撤回商品。
  • 模拟器对账采用每 60 秒调度和按需触发，作为演示配置；真实频率受平台配额和业务风险约束。
  • 死信保存分类、尝试历史、最后回执和建议动作；手工重试需原因，不清零审计；重试仍验证版本与时效。

状态表示业务事实，进度表示任务执行。不要用一个“成功/失败”字段承载导入、匹配、审批和发布的全部含义。

不可违反的规则

  1. 任何跨租户外键关系都必须被数据库或资源检查拒绝。
  2. APPROVED 映射必须引用来源实体版本与主数据版本；关键事实变更后不能继续静默有效。
  3. 已审批快照的业务 payload 永不可变；审批记录中的 hash 必须与任务实际 hash 相同。
  4. 任一库存池的静态渠道分配总额不超过扣除缓冲后的可用量；两个价格计划引用同池不重复加总。
  5. 同 listing 的 desired_revision 单调递增；旧任务不能把远端 revision 降级。
  6. 无法确认的渠道结果必须为 UNKNOWN；不得在列表中伪装为“已发布”。
  7. 重试不能修改 payload 或换用已过期的库存；重发相同业务效果复用稳定幂等键。
  8. 激活来源与写 outbox 同事务；远端 HTTP 调用不放进数据库长事务。

并发与取消

领域聚合使用 version/ETag 乐观锁。任务租约带 owner、expires_at、fencing_token；租约超时的旧 Worker 不得更新本地结果。取消仅取消未发送任务；SENDING/UNKNOWN 必须先确认外部效果。需要撤回时创建更高 revision 的停卖操作，不能用删除任务假装远端操作消失。

技术架构与模块规格

后端主线：持久化工作流，而非 Agent 自主规划

阶段顺序、转换条件和副作用由服务端代码与版本化策略决定。AI 只作为被调用的能力，不拥有发布权限。编排器负责“现在可以执行什么”，Worker 负责“如何执行该阶段”，领域模块负责“该操作是否合法”。第一版可用 PostgreSQL 实现轻量编排，不必引入额外工作流平台；人工长等待和流程迁移复杂后，再评估专用持久化工作流引擎。

事务、并发与背压

  • 事务 A：保存阶段结果、状态转换、审计与后续 outbox 同事务提交。模型/解析/HTTP 在事务外执行，完成后按租约 token 与预期版本提交结果。
  • 事务 B：激活来源时锁分区并递增版本。多分区按固定顺序加锁；死锁/序列化失败可有限重试，不能静默覆盖。
  • 事务 C：创建发布计划时检查快照、来源、映射和审批/策略版本；发送前再次校验。已过时任务停止并生成新运行。检查后仍可能出现外部在途竞争，使用远端 revision 和后续对账处理，不能宣称完全消除所有竞态。
  • 资源隔离：解析、AI、渠道调用使用不同并发预算；按租户公平调度，渠道账号独立限流。队列超过阈值拒绝新重型任务或排队告知，避免无限积压。
  • 崩溃恢复：租约到期才接管；旧 Worker 的本地提交被 fencing token 拒绝。外部调用另靠业务幂等与远端 revision 保护，租约本身不能防止外部重复效果。
  • 局部恢复：有效输出按 input_hash 复用；新来源使依赖步骤失效。修复坏数据产生新批次并关联旧 run，不把旧快照 payload 原地更新。

自动化控制面

管理员可暂停租户、供应商或渠道的新增派发；已 SENDING/UNKNOWN 的任务仍需查询与对账。区分“暂停运行”“取消未发送任务”“紧急停卖”三种动作。人工待办显示阻断原因、影响范围、负责角色和恢复条件；完成决策后自动恢复后续阶段。首版用 job 查询轮询即可，不为展示引入 WebSocket。

错误约定

400 参数错误；401 未认证；403 无权；对不可见资源可统一 404 防枚举；409 版本/幂等冲突；413 文件超限；422 业务语义不可满足；429 限流；503 短暂不可用。error.code 稳定用于前端动作，message 可本地化，details 不含密钥/SQL/堆栈。异步 job 失败使用相同错误结构，不让 HTTP 202 被误读为业务成功。

租户隔离的实际实现

  • API 令牌携带用户身份，服务端通过 membership 验证 active tenant；不信任请求体中的 tenant_id。对象 ID 每次按租户过滤并做动作权限检查。
  • PostgreSQL RLS 作为第二道边界，事务内使用 SET LOCAL 设置租户；连接池归还前不遗留上下文。服务角色不使用 BYPASSRLS，必要时 FORCE ROW LEVEL SECURITY。
  • 后台任务从数据库取 tenant 上下文并校验任务归属；artifact 路径、向量检索、缓存 key、幂等 key、日志索引和指标查询均带租户作用域。
  • 复合 FK 防止“本租户 mapping 指向他租户酒店”；共享候选索引默认禁用。管理员也只管理所在租户，平台运维越权访问需要显式 break-glass 流程。
  • 本地登录可使用开发账号，但密码哈希、会话过期、HttpOnly/SameSite Cookie、CSRF 防护和登录限速仍需实现；联网部署必须 HTTPS。

拟议告警与处置手册

  • 停卖待确认超过 5 分钟：演示阈值；先查询远端，暂停新发布，提升停卖优先级，记录受影响日期，不把任务重置为成功。
  • UNKNOWN 积压 / 429 持续：检查远端健康与配额，降低账号并发，防止重试风暴；确认最大等待和人工责任人。
  • 来源 TTL 过期：标记报价失效，创建关闭目标，通知补文件；远端查询失败时保持风险可见。
  • 映射误判：冻结映射→影响分析→停卖→修订→复审→发布→对账；保留 incident 记录用于评估。
  • 数据库恢复：先停止发新任务，恢复备份与日志，校验快照 hash；以外部幂等收据和远端状态重建 applied，不盲目重播所有事件。

恢复目标（拟议，待验证）

本地展示版本可接受 RPO≤24h、RTO≤1h，需用备份/恢复演练证实后才能写成结果；真实商业系统的 RPO/RTO 由合同与收入风险决定。备份包含数据库、原件存储与版本清单，恢复演练必须覆盖“远端成功、本地尚未记账”的窗口。

测试策略、AI 评估与目标指标

验收优先级：业务正确性 → 故障恢复 → 性能与可运维性 → AI 辅助效果

后端必测不因模型准确率高而豁免。AI只需至少一项实际能力接入、结果可验证、失败可降级；更高匹配准确率属于后续优化。既要证明常规流程能自动完成，也要证明异常不会被错误地当作成功。

为什么不能轻易承诺 99% 自动匹配

高置信建议精确率必须同时给出样本量、覆盖率与置信区间。若只在少量容易样本上全部正确，不能支撑 99% 泛化声明。未来启用自动批准前，应以足够独立样本证明误合并上界可接受，并由业务负责人确定风险预算；任何硬冲突仍不得自动通过。

MVP 总验收清单

  1. 纵向闭环在同一运行实例中贯通，包含至少一项实际AI能力；不以未实现的设计描述替代执行证据。
  2. 符合授权策略的常规更新自动完成；策略外异常进入持久化等待，人工处理后从检查点恢复；策略停用、重复决策与来源变化均有测试。
  3. 三种本地文件格式可走相同契约；保留原件与行定位；覆盖范围与增量/全量明确。
  4. 相同文件重复处理不重复生效；旧版本不能覆盖新分区；坏行不会被当成全量删除。
  5. 酒店、房型、计划独立映射；Twin/King、可退/不可退、未知税费的必测冲突不能自动通过。
  6. AI 不可用时，人工审核、编译、审批与模拟发布仍可完成；每个提案能显示证据与版本。
  7. 报价金额可复算；共享库存池不重复计算；静态渠道分配总额符合约束。
  8. 审批绑定不可变快照；关键来源变化或审批过期时禁止发布；新 revision 可重编译审批。
  9. 模拟器独立落地，具备幂等、回执、revision 与故障注入；不会触达真实平台。
  10. 重复投递、落地后超时、Worker 崩溃、429、迟到旧版本和部分失败都有明确处理与测试。
  11. 对账区分 missing/drift/unknown，修复不复活停售商品；发布状态可追到远端观察结果。
  12. 租户/权限负向测试通过；来源文本安全呈现；导出与模型输入无越权泄露。
  13. 有固定演示数据、重置命令、完整审计回放和可复现测试报告；所有实测数字注明环境和时间。
  14. README 明确当前实现、未实现与真实接入边界；不将设计文档内容全部冒称已实现。

建议砍掉的首版复杂度

不做自动预订、儿童年龄价格、复杂打包套餐、多币种实时汇率、真实税费引擎、全球内容爬取、微服务集群、自动政策放宽和全自动实体合并。保留数据库可扩展点即可，不为未来功能预建大量空页面。

未来供应商 API 与真实渠道接入

不假设 OTA/B2B 提供可自助申请的开放 API，也不承诺某个平台一定接受本企业成为供货方。真实接入对象和条件尚未研究验证，本节定义研究与准入方法，而非平台事实清单。

供应商 API 扩展

连接器把拉取/推送数据变为同样的 raw artifact + normalized version，不绕过质量检查与激活规则。增加游标、增量版本、限流、断点、凭证轮换与 webhook 验签；重复/乱序事件按供应方序号处理。若 API 只有当前快照，需定义抓取窗口一致性与缺失项语义。现有系统连接器优先受支持的导出/API，不直接依赖其内部数据库表。

真实渠道适配器研究清单

  • 商品内容、房型、计划、价格、库存、限制是否分别维护？内部与渠道编码由谁创建和确认？是否需要先人工建店？
  • 每晚/每次入住、含税/净价、人数组合、儿童、早餐和取消阶梯能否无损表达？不能表达时阻断还是需要独立商品？
  • 请求是 upsert、patch 还是替换？最大日期范围、部分失败、异步回执、读取一致性和限流规则是什么？
  • 是否支持幂等键、更新版本或 operation 查询？若不支持，如何降低重复与迟到覆盖风险？残余风险由谁接受？
  • 停售是否有高优先级通道？远端状态多久可读到？时钟、时区、金额舍入和错误码如何处理？
  • 真实共享库存与订单是否闭环？若不能回流订单，是否只允许独占 allotment 或人工受控分配？

避免不可逆的接口耦合

核心存标准商品语义和来源证据，渠道映射与 payload 保存在 adapter 层；渠道回执归一化同时保留原响应引用。新增渠道需通过能力契约和回归测试，不能修改核心政策使其迁就单个平台。真实凭证与演示配置分开，生产适配器默认不存在或禁用。

决策选择与理由代价 / 重审条件

可直接用于开发的首批任务

  1. 冻结术语与文件 Schema v1，制作一份有效包与五份异常变体，手工写出期望结果。
  2. 建立独立项目环境、数据库迁移、tenant/membership/RLS 与负向权限测试。
  3. 实现原件上传、hash、preview 和 staging，不调用模型；把坏行与覆盖范围语义做正确。
  4. 先完成主数据/映射审核与规则候选，以最少页面打通到模拟器的纵向链路；保留可替换模型接口。
  5. 用纯函数实现报价编译、共享库存分配和不可变快照；完成金额/日期/政策测试。
  6. 建立模拟器，再做外盒、幂等与 UNKNOWN；用“远端已写入但本地超时”作为首个可靠性用例。
  7. 完善持久化等待、并发控制、对账与审计；再接入至少一项实际AI能力及授权策略自动流转，最后完善后台，按P0清单冻结版本。

面试表达建议

先用一条纵向业务链解释领域模型，再展示重复导入、并发激活、人工等待恢复、发布超时与对账修复。结合事务边界、唯一约束和测试结果说明正确性；AI用一组实际输入输出展示其辅助作用。最后指出本地文件库存与模拟渠道的真实性边界。只有完成实测后，才把“建议目标”改成“在某环境某数据规模下测得”。

交付定义

成功的作品不是功能菜单最长，而是能把一份来源不统一的文件，经过可解释判断、明确审批与可靠执行，变成一份可核对、可追溯、可恢复的模拟渠道商品。每一个“自动化”都应能回答：依据什么、谁批准、失败怎么办、如何证明。
